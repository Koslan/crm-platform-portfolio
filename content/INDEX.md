# content/ — рабочая копия всех текстов и диаграмм сайта

**Если вы новый чат и вам дали этот файл — прочитайте его целиком, потом `STRUCTURE.md`.
Этого достаточно, чтобы работать с проектом, не читая 2 500 строк `src/app.html`.**

## Что это

Односторонний экспорт **всей прозы и всех спек диаграмм** портфолио-сайта
(`crm-portfolio-site`) в markdown — чтобы править тексты, не залезая в код.
Здесь ~15 200 слов: 18 страниц портфолио, 5 вкладок, карта навыков, подсказки, схема интеграций,
5 диаграмм.

**Источник правды — по-прежнему `src/app.html`.** Эти файлы — копия. Правка md сама по себе
на сайт не попадает.

## Как читать страницу

У каждого файла в `pages/` есть front-matter с точным адресом текста в коде:

```yaml
page: cross-system
type: "write-up (CASES → vCase)"     # какой архетип, см. STRUCTURE.md
route: "#/p/cross-system"
source:
  nav: src/app.html · ZOHO_GROUPS · id="cross-system"       # заголовок + подпись карточки
  body_case: src/app.html · CASES['Integration and sync'][0] # текст страницы
```

`type` определяет, что можно менять, ничего не ломая:

| type | Свобода правки |
| --- | --- |
| `write-up (CASES → vCase)` | полная: секции добавляются, удаляются, переставляются |
| `live-demo (общий шаблон viewRecord)` | структура жёсткая — только `sub`, список «What to try», `why` |
| `live-demo/write-up (свой рендерер PAGE)` | проза внутри разметки, правится по совпадению строки |

## Как читать диаграмму

Каждая диаграмма в md идёт двумя частями:

1. **Читаемый вид** — таблица (матрица владения), нумерованный список (цепочка) или
   вход → правила → корзины (воронка). Это для чтения и обсуждения.
2. **`<details>` со спекой в JSON** — **вот это и есть источник.** Правите его.
   Читаемый вид пересоберётся сам при следующем экспорте.

Ключевые поля спеки: `kind` (chain / authority / funnel), `at` (после какой секции `body`
вставить), `aria` (альт-текст для скринридера — обязателен), `detail` (что показывается
при клике по элементу). Подробнее — `STRUCTURE.md`, раздел «Диаграммы».

## Как применить правку обратно в сайт

Автоматического применятора **пока нет** — сознательно. Порядок такой:

1. Правите нужный md.
2. Говорите в чат: «примени `content/pages/cross-system.md`» (или несколько файлов).
3. Чат находит место по `source` из front-matter, переносит текст в `src/app.html`,
   прогоняет `npm run build && npm test`, показывает диф.
4. После применения — `node content/_export.mjs`, чтобы копия снова совпадала с кодом.
   Экспортёру нужен `turndown` (`npm i -D turndown`, один раз) — единственная зависимость
   сверх проектных, и нужна она только ему: сборка сайта её не трогает.

### Чего нельзя ломать при правке

- **Front-matter.** Он и есть адрес правки. Особенно `source` и `page`.
- **Заголовки `##` внутри страницы** — это заголовки секций `body`, они видны на сайте.
- **Апострофы.** Тексты уезжают в JS-строки в одинарных кавычках. В коде используется
  типографский `’`, не прямой `'` — если ставите прямой, при применении он экранируется.
- **`aria` у диаграмм.** Пустой alt-текст роняет `smoke-diagrams.mjs`.
- **`at` у диаграммы.** Индекс секции, после которой она встаёт. Добавили секцию выше —
  сдвиньте `at`, иначе картинка окажется не в том месте.
- **Числа, которые проверяются тестами:** `TEST_COUNT` (240) упоминается в `harness.md`
  и `ai-workflow.md`; количество шагов и ячеек диаграмм проверяется в `smoke-diagrams.mjs`
  (цепочки ≥7 и ≥6 узлов, матрицы ≥24 и ≥10 ячеек, воронка ≥6 корзин).

### Чего нельзя писать никогда

CI роняет сборку за реальные идентификаторы: домены и хосты Zoho-орга, org id, названия
модулей исходного орга, что-либо похожее на токен или ключ. Имена работодателей в CV-части
разрешены, идентификаторы их систем — нет. Сканер — второй гейт в `.github/workflows/deploy.yml`.

## Что бросается в глаза прямо сейчас

Не правки, а наблюдения — решать вам:

- **Половина текста сайта — на About** (`skills-map.md` + `skill-tips.md` = 7 200 слов).
  Живые демо, ради которых всё построено, несут ~240 слов на страницу.
- **`cross-system.md` — 1 915 слов**, 39% всего объёма лонгридов и в 2,3 раза больше следующего.
  Он отвечает на три разных вопроса («кто прав», «что перезаписывать», «где остановиться») —
  при желании режется на три статьи по ~600 слов.
- **Цифры в шапке About разошлись с реальностью.** Hero говорит «15 live demos» и «21 write-ups» —
  это захардкожено в `vAbout()` (строки ~1489–1490). Фактически после двух чисток на сайте
  **9 живых демо и 9 лонгридов**. Блок «08 / THIS SITE, LIVE» на той же странице считает
  честно, через `demoCount`/`writeupCount` — то есть на одной странице стоят два разных числа.
  Чинится заменой двух литералов на те же переменные. Это единственная фактическая ошибка,
  которую я нашёл при экспорте.
- **Два мёртвых текста.** `agent-journal.md` и `sf-sync.md` содержат записи в `CASES`,
  которые никогда не рендерятся, потому что `PAGE` перекрывает `CASES`. Помечено в файлах
  блоком «⚠️ Мёртвый текст». Их стоит либо удалить, либо влить в рендерер.
